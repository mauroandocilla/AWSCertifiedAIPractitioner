# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
npm install       # install dependencies
npm run dev        # start Vite dev server (serves at /AWSCertifiedAIPractitioner/, matching production base path)
npm run build       # tsc -b (typecheck) && vite build → output in dist/
npm run preview      # serve the production build locally
```

There is no test suite and no lint script configured — don't invent one.

Every script in `scripts/` (the original quiz pipeline, the quiz-v2 pipeline, and the domain-audio pipeline) is **not** wired into `package.json` and is **not part of normal development** — see "Quiz content pipeline", "Quiz v2", and "Spoken glossary + read-aloud audio" below before touching any of them.

## Architecture

This is a React 19 + TypeScript + Vite 6 single-page app: a study guide **and practice-quiz/exam-simulator** for the AWS Certified AI Practitioner (AIF-C01) exam, with a read-aloud audio mode on the glossary. All content and UI copy is in Spanish by default; the quiz has an ES/EN toggle. Code/identifiers are in English.

### Routing

`HashRouter` (from `react-router-dom`), not `BrowserRouter` — deliberate, because the app is a static GitHub Pages deploy with no server-side rewrite rules, so hash-based routes work without a 404-redirect trick. `vite.config.ts` sets `base: '/AWSCertifiedAIPractitioner/'` to match the GitHub Pages project-site path.

`src/App.tsx`: `/` (`Landing`, outside the layout) plus a shared `<Route element={<Layout />}>` wrapping every other route: `/dominio/:n`, `/servicios`, `/glosario`, `/mapa-conceptual` (see "Concept map" below), `/recorrido` (see "Study journey checklist" below), `/mapa-de-experiencia` (see "Experience map" below), `/como-estudiarlo`, `/formato-examen`, `/quiz` (set list), `/quiz/:setNumber` (a quiz session), `/quiz-v2` (the newer single-set bilingual quiz, see "Quiz v2" below), `/examen` (timed exam simulation). Adding a route means updating four places in lockstep: the `<Route>` itself, `QuickJumpBar.tsx`'s `ITEMS` list, `Layout.tsx`'s `currentFromPath()` (so the right pill highlights), and usually a card in `Landing.tsx`'s grid. `Layout.tsx` renders `QuickJumpBar` + `<Outlet/>` **once** — `current` for the pill highlight is derived from the URL (`useLocation`/`useParams`) inside `QuickJumpBar` itself, not passed in by each page. This exists specifically so `QuickJumpBar` doesn't unmount/remount on every navigation (it used to, per-page, which reset the pill row's scroll position — don't go back to that pattern). `ThemeToggle`, `ScrollToTop`, `DomainSearch` (the global Ctrl+K search overlay), and `NowPlayingButton` (see "Global read-aloud audio session" below) also mount once in `App.tsx`, outside `Routes`.

### Global search (`Ctrl+K`)

`DomainSearch.tsx` is a fuse.js-powered overlay searching `domainSearchIndex` (`src/domainSearch.ts`), which flattens every domain bullet plus every term-card inside its glossary explanation (via `glossaryCards.ts`'s shared HTML parser) into one flat, fuzzy-searchable list — built once at module load since domain/glossary content is static. Selecting a result navigates to `/dominio/:n?b=<glossId>` and passes `highlightCardIndex` as router *navigation state* (not a URL param), so `DomainDetail.tsx` can scroll to and flash the exact match — deliberately kept out of the URL so a page reload or a shared link never re-triggers the flash.

### Content is data-driven, not hand-authored JSX

`src/domainData.ts` and `src/glossaryData.ts` hold ALL of the domain/glossary exam content (structure + prose) as plain data — components read from them, they don't contain prose. Originally generated by `scripts/extract-content.mjs`, a one-off parser that pulled content out of an earlier single-page HTML version of this guide. That script does not need to run again — **when correcting or adding domain/glossary content, edit `domainData.ts`/`glossaryData.ts` directly**.

Content-accuracy convention: this content was audited bullet-by-bullet against the official AWS exam guide (docs.aws.amazon.com/aws-certification). Any term/service mentioned that is NOT part of the official quoted objective text is marked inline as `<h4>Name <em>(extra, no está en el bullet oficial)</em></h4>` with a `<p><em>Fuente: ...</em></p>` line citing where it came from. Keep following this pattern for any future non-official addition — never blend third-party content into a bullet's "official" quoted text.

### Domain pages: master-detail layout

`src/components/DomainDetail.tsx` is the one component every `/dominio/:n` route uses — it reads the domain's subsections/bullets from `domainData.ts`. Desktop layout is a two-column master-detail: a left sidebar lists every bullet (grouped by subsection); clicking one shows that bullet's glossary explanation in the right panel via `GlossaryEntryContent`, driven by a `?b=<glossId>` query param on the same route. The sidebar is `position: sticky` (top `92px`, `max-height: calc(100vh - 92px)`) — it stays pinned while the panel scrolls but naturally releases once its containing row reaches the footer. Don't change this to `fixed` without re-solving the footer-overlap problem that motivated `sticky`. On mobile it collapses to `position: static` (see "Mobile layout" below) and `QuizSessionPage.tsx`'s sidebar reuses this exact same sticky pattern on desktop.

`/glosario` reuses the same `GlossaryEntryContent` renderer, plus an index and a `?t=<glossId>` deep-link that scrolls to and highlights one entry.

### Global read-aloud audio session

Every glossary entry exists in two versions: `src/glossaryData.ts` ("Técnico", the official audited text) and `src/glossaryDataSpoken.ts` ("Profesor", prose rewritten for being read aloud — generated from the técnico version per `others/spoken-glossary-brief.md`, gitignored). `GlossaryEntryContent.tsx` has a Técnico/Profesor toggle (`localStorage` key `glossary-display-mode`) controlling which one is *displayed* — but **read-aloud audio always narrates the Profesor version**, regardless of that toggle; this is a deliberate design decision, not a bug.

`src/glossaryCards.ts`'s `buildReadAloudSegments()` is the single source of truth for how an entry is split into speakable pieces (bullet text, then each term-card's title/paragraph/short-summary) and how each piece's stable id is built — shared between the live browser-voice path and `scripts/generate-domain-audio.mjs`, so the frontend's queue and the pre-rendered audio files always line up by id.

Two interchangeable playback engines share one hook API (`status/activeIndex/rate/setRate/currentTime/duration/seek/seekTo/playAll/playRange/pause/resume/stop`), picked at runtime by `useAudioAvailable.ts`:
- `useReadAloud.ts` — the browser's `window.speechSynthesis` (`es-ES`), always available, no setup needed. `currentTime`/`duration` are always 0 and `seek`/`seekTo` are no-ops — the Web Speech API exposes no per-utterance position, so there's nothing real to report.
- `useAudioReadAloud.ts` — plays pre-rendered MP3s through a real `<audio>` element from `AUDIO_BASE` (`src/audioBase.ts`) + `${segmentId}.mp3`, and wires `navigator.mediaSession` for lock-screen play/pause/prev/next. Real `currentTime`/`duration` come from the `<audio>` element itself; `seek(deltaSeconds)` hands off into the neighboring segment (with the right offset) when a skip overshoots the current one's start/end, so a ±5s skip near a segment boundary still moves roughly 5s of actual audio.

`useAudioAvailable` is optimistic by default (assumes the real audio exists) and only falls back to the browser voice the first time an actual playback attempt errors — cached at module scope so one failure disables audio for the rest of the session. This is deliberately *not* an upfront probe: iOS Safari won't reliably fire load events for an `<audio>.load()` not triggered by a user gesture, so an upfront check could hang forever and permanently fall back even when the audio is genuinely there.

**The engine and its player UI live in `GlossaryAudioProvider.tsx`, mounted once in `App.tsx` above `<Routes>` — not inside `GlossaryEntryContent.tsx`.** That's deliberate, fixing two bugs that were side effects of a per-instance approach: rotating the phone crosses the same 720px breakpoint `DomainDetail.tsx` uses to switch its whole layout branch, which used to unmount/remount whatever was reading aloud as a side effect; and the floating player's `position: fixed` would end up pinned to the bottom of a mobile slide-pane's *content* instead of the viewport, because that pane's CSS animation leaves a permanent `transform: translateX(0)` on itself after finishing (`animation-fill-mode: both`) — and per spec, *any* non-`none` transform on an ancestor, even a no-op one, makes that ancestor the containing block for a `position: fixed` descendant. Living outside any per-page layout sidesteps both structurally. `GlossaryEntryContent.tsx` and `ResumeListeningBanner.tsx` just consume `useGlossaryAudio()`; a given instance only treats state as "about me" when `session.entryId === id`, since some other entry (possibly on a page you've since navigated away from) may be what's actually playing — playback is intentionally independent of whatever page is currently visible, podcast-style.

Also owned by the provider:
- **Continuar escuchando**: the single most recent playback position across the whole app (entry, segment, exact second) — not a per-entry completion tracker — saved to `localStorage` (`glossary-audio-resume`) on pause/stop/tab-hide/close and every few seconds while playing. `ResumeListeningBanner.tsx` (shown on Landing and `/glosario`) and the `nowPlayingOpen` full-screen view below both read `resumeState`/call `resumeEntry()`.
- **Cross-bullet advance**: `stepCard()`'s "next concept" falls through into the next bullet in reading order (`orderedGlossIds`, flattened from `domainData.ts` the same way `domainSearch.ts` does) once the current entry's own term-cards run out, instead of just stopping — a continuous listen across the whole glossary, not one bullet at a time. Symmetric going backward (lands on the *previous* bullet's last card, not its first).
- **`entryContentUrl`/`contentNavTarget`**: "ir al contenido" (in the mini-player, the resume banner, and the full-screen view) mirrors `DomainSearch.tsx`'s `goToResult()` exactly — `highlightCardIndex` travels as router navigation state, which is what makes `GlossaryEntryContent.tsx` actually scroll to and flash the target (a bare `?b=` query param does neither). That target also carries a `nonce` (`DomainDetail.tsx`'s `highlight` state, not the URL) — without it, navigating to a card you were *already* looking at passes the exact same `highlightCardIndex` value as last time, and React skips the effect entirely since nothing in its dependency array changed. Also: `GlossaryEntryContent.tsx`'s scroll effects are deliberately delayed ~320ms (past `.mobile-pane`'s slide-in animation) — calling `scrollIntoView` while that animation is still running measures a target that's still moving, landing a card or two off once it settles.
- **Now Playing**: `NowPlayingButton.tsx` is a persistent header icon (present on every page, unlike the resume banner or the mini-player) that opens a full-screen overlay (`nowPlayingOpen` state) showing whatever's playing, or the resume prompt if idle, or an empty state.

The floating mini-player and the full-screen view share their progress-row/controls-row JSX (`renderProgressRow()`/`renderControlsRow()` inside `GlossaryAudioProvider.tsx`, reused via CSS descendant selectors under `.now-playing-card` for the bigger scale, not duplicated markup).

The pre-rendered audio itself is **not built or served through this repo's normal `npm run build`/`dev` flow** — it's a manual, personal pipeline, run outside Claude Code:
1. `scripts/generate-domain-audio.mjs` — synthesizes every segment via **Azure neural TTS** (voice `es-MX-JorgeMultilingualNeural`, used for both Spanish and English runs since it's multilingual — needed because Azure's SSML `<lang>` mid-utterance switching silently didn't work). Splits each segment into Spanish/English runs, synthesizes each separately, and splices them with `ffmpeg` (`brew install ffmpeg` required). Needs `AZURE_SPEECH_KEY` + `AZURE_SPEECH_REGION` env vars (Azure Speech resource, free tier). Subcommands: `test` (3 samples → `others/domain-audio-test/`), `generate` (full run → `public/domain-audio/`, skips existing files, safe to re-run), `stats` (no API calls).
2. `scripts/check-audio-truncation.mjs` — no network calls, uses `ffprobe` to flag locally-generated files that are suspiciously short for their source text (an Azure TTS truncation bug). `--delete` removes flagged files and prints the matching `FORCE_FILES=...` line for re-upload.
3. `scripts/upload-domain-audio.mjs` — uploads `public/domain-audio/*.mp3` to a **Cloudflare R2** bucket (not GitHub Releases — Releases forces `Content-Disposition: attachment` + `application/octet-stream` on every asset, which iOS Safari refuses to play; R2 lets each file get a real `Content-Type: audio/mpeg`). Needs `R2_ACCOUNT_ID`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`; optional `R2_BUCKET`. `FORCE_FILES=a.mp3,b.mp3` re-uploads specific files even if already present; `FORCE_ALL=1` re-uploads everything (needed after swapping the underlying source text without changing filenames).

`others/` (gitignored) holds all raw/staging audio and the spoken-glossary brief — none of it is committed or bundled into the deployed app; only the small `AUDIO_BASE` URL pointer in `src/audioBase.ts` is. **Same rule as the quiz content pipeline below: run these manually when the user explicitly asks, never proactively — they cost real money on the configured Azure/Cloudflare accounts.**

### Icons

`lucide-react` — every icon in the app is a direct import from it (`import { Play, Pause, X, ... } from 'lucide-react'`) at the call site, no per-icon wrapper components. The two exceptions are `SkipBackIcon.tsx`/`SkipForwardIcon.tsx`, which composite a lucide rotate-arrow glyph with the actual seconds count overlaid as text (there's no "skip N seconds" icon in any library) — keep those two, but don't add a new wrapper file for a plain 1:1 icon re-export; that's an indirection with no benefit once the underlying icon is a library import rather than custom SVG.

### Concept map (`/mapa-conceptual`)

`ConceptMap.tsx` force-directs (`d3-force` + `d3-zoom`, both hand-rolled SVG rendering, not a canvas/WebGL library) a graph of individual glossary *terms* (not whole bullets) — `src/conceptGraph.ts`'s `conceptEdges` is a hand-curated list of `{ from, to, relation, note? }`, where `relation` is one of `requiere | ejemplo-de | se-usa-con | contrasta-con` and node ids are `${glossId}#${cardIndex}` (the term-card's zero-based position within that entry's html, same positional scheme `domainSearch.ts` already relies on). There is no separate node list — nodes are derived at runtime from whatever ids appear in `conceptEdges`, looking up title/domain live via `glossaryById` + `parseGlossaryCards()` so they can never drift out of sync with the actual glossary content. A dev-only sanity check at the bottom of `conceptGraph.ts` (`import.meta.env.DEV`-gated) warns on any edge whose id doesn't resolve to a real entry/card index — hand-curated ids are exactly the kind of thing that silently typos.

The simulation runs entirely outside React's render cycle: `nodes`/`links` are built once (`useMemo`, never `useState`, since `d3-force` mutates them in place every tick) and each tick writes straight to DOM attributes via refs — committing 300+ node positions through React state 60 times/sec would re-render the whole tree every frame. A synchronous pre-tick burst (300 ticks) runs before the SVG is even shown, so the layout doesn't visibly fly in from its starting positions.

**On curation quality**: the first curation pass (hand-picking real conceptual connections while reading all 310 term-cards) produced 51 disconnected clusters — mostly lonely pairs/triples that, under pure `forceManyBody` repulsion with nothing else pulling on them, drift arbitrarily far from the main mass and read as "nothing connects to anything" even though within their own tiny cluster they do. Two mitigations, both worth keeping in mind before curating more: (1) a second curation pass specifically added bridging edges between the smaller clusters to collapse them down to a couple of large, cohesive ones; (2) the simulation also runs a weak per-node `forceX`/`forceY` pulling every node toward center regardless of connectivity, so any cluster that's still small stays near the middle instead of drifting off-canvas. If you add more curated edges later, sanity-check the resulting connected-component count (a quick throwaway script: regex out every `from`/`to` pair, flood-fill an adjacency map) rather than assuming more edges automatically means a more cohesive-looking map.

### Study journey checklist (`/recorrido`)

`StudyJourneyPage.tsx` is a manual checklist over the *existing* `domainData.ts` structure (domains → subsections → bullets) — no new content file. There's no automatic way to know someone actually studied a bullet (unlike the quiz's answered/correct tracking or the audio player's resume position), so completion is self-reported: clicking a bullet's checkbox toggles `Record<glossId, boolean>` persisted to `localStorage` (`study-journey-progress`). Per-domain and total completion reuse `ProgressRing.tsx` (the same ring `QuizSessionPage.tsx`'s sidebar already uses for per-set progress).

### Experience map (`/mapa-de-experiencia`)

`JourneyMapPage.tsx` is a different thing from the two pages above — a classic UX-research *journey map* (persona, actions, behavior, feelings, a mood curve, an opportunities row), not a network graph or a checklist. `STAGES` is a fixed, hand-written array (6 stages of preparing for the exam); the mood curve is a small hand-rolled SVG line chart (one series, single accent hue — no library, this isn't a data-exploration chart). The "opportunities" row is the point of adapting this format to an app rather than a static diagram: each stage links to whatever real feature of this app helps at that point (e.g. the quiz stage links to `/quiz`, the exam-prep stage links to `/examen`). All rows render as one flat CSS grid (`.jmap-grid`, `grid-template-columns: 110px repeat(6, ...)`) rather than nested per-row grids — a nested grid would let each row size its own columns off just that row's content, so the same stage's column could end up a different width in the "Qué hace" row than in the "Cómo se siente" row, breaking the one thing a journey map needs (reading a column top-to-bottom as one coherent stage).

### Quiz system

Practice quiz content lives in `src/quiz/data/set-N.json` (English) and `src/quiz/data-es/set-N.json` (Spanish) — 21 sets, numbered 1–5 and 9–24 (sets 6–8 were dropped for being off-topic). `src/quiz/meta.ts` is an auto-generated index of `{setNumber, questionCount}` per set — **regenerated by the pipeline scripts, don't hand-edit**. `loadSet.ts` uses `import.meta.glob` scoped per language directory so opening `/quiz/:n` only fetches that one set's JSON chunk. `useQuizLang.ts` is a small `localStorage`-backed `es|en` toggle (key `quiz-lang`) read by every quiz/exam page. `QuizSessionPage.tsx` persists per-set answered/revealed state to `localStorage` under `quiz-progress-{setNumber}`.

`types.ts` defines `QuizQuestion`: options, `multiSelect`, `explanationHtml` (raw HTML rendered via `dangerouslySetInnerHTML` — trusted because it's our own generated content, not user input), and an optional `domain` (1–5) used by exam sampling below.

### Exam simulation mode (`/examen`)

`ExamPage.tsx` runs a `setup → active → results` flow (local component state, no route param for phase). A `source: 'original' | 'v2'` toggle on the setup screen (default `'original'`) picks which question bank to sample from — "SkillCertPro" (the original quiz, `loadOriginalExamPool`) or "TutorialsDojo" (quiz-v2, `loadQuizV2ExamPool`) — both normalize into the same `ExamQuestion[]` shape (`quiz/examTypes.ts`) so the rest of the exam flow doesn't care which source was picked. 65 questions, a 90-minute countdown that auto-finishes at zero, and — unlike the practice quiz — **no per-question feedback during the exam**, only flag-for-review and a question-navigator grid. `examSampling.ts` samples the 65 from the full question pool (`loadAllQuestions.ts`, which concatenates every set) proportionally to each domain's real weight from `domainData.ts`, bucketing by each question's tagged `.domain`; it falls back to a plain shuffle if fewer than half the pool is domain-tagged yet. The results screen shows score + a full review with explanations, with an explicit disclaimer that this is an approximation, **not** AWS's real 100–1000 compensatory-scored scale.

### Quiz v2 (`/quiz-v2`)

A second, newer practice-quiz system that coexists with (does not replace) the original one above. Key differences: all content lives in **one bilingual JSON file**, `src/quiz-v2/data/questions.json` — every field is a `{en, es}` `Localized` pair (`quiz-v2/types.ts`) so the two languages can never drift into separate out-of-sync files the way the original quiz's `data/`/`data-es/` folders can. It's a single continuous set (no set list/selection), rendered by `QuizV2Page.tsx`, with its own `localStorage` progress key `quiz-v2-progress`. It adds a third question type beyond single/multiple: `matching` (several prompts, each answered by picking from a shared pool of choices). `quiz-v2/resolveLang.ts` projects the raw bilingual shape down to one language at render/sampling time; `quiz-v2/withBasePath.ts` rewrites root-relative `/quiz-other-images/...` image `src`s in explanations to respect Vite's base path.

Source content is TutorialsDojo's practice tests (vs. the original quiz's SkillCertPro source). Pipeline (manual, outside Claude Code, mirrors the rules below):
1. `scripts/build-quiz-other.mjs` — dedupes/cleans raw TutorialsDojo exports from `others/quiz-other/` into `others/quiz-other/merged.json`. Pure text parsing, no LLM calls, no cost.
2. `scripts/export-quiz-v2.mjs` — additively merges `merged.json` into `questions.json` (English only; ids already translated/tagged are left untouched).
3. `scripts/translate-quiz-v2.mjs` — Anthropic Batch API (`claude-haiku-4-5`), adds the `{en, es}` pairs. Subcommands `test|submit|status|collect|retry`.
4. Alternative free-MT path: `scripts/export-quiz-v2-for-matecat.mjs` (exports English text for MateCat) + `scripts/build-quiz-v2-glossary-tmx.mjs` (builds a TMX glossary of AWS/technical terms so MateCat's MT stops mistranslating them) → `scripts/fix-quiz-v2-service-names.mjs` + `scripts/fix-quiz-v2-service-names-manual.mjs` (mechanical/hand-curated fixes for AWS service names MateCat still mangled).
5. `scripts/tag-quiz-v2-domains.mjs` — Anthropic Batch API, tags each question's exam domain (1–5); quiz-v2 content is pre-confirmed in-scope, so unlike the original quiz's pipeline there's no separate scope-classification step. Subcommands `test|submit|status|collect`.

### Quiz content pipeline (manual, outside Claude Code — original quiz only, see "Quiz v2" above for that system's own pipeline)

`scripts/extract-quiz.mjs`, `translate-quiz.mjs`, `classify-quiz-scope.mjs`, and `apply-quiz-scope-cleanup.mjs` build the quiz content from raw source material in `others/quiz/` (gitignored — third-party practice-test HTML, not ours to redistribute):

- `extract-quiz.mjs` — parses the source HTML → `src/quiz/data/set-N.json` + regenerates `meta.ts`.
- `translate-quiz.mjs` — EN → `data-es/` via the Anthropic Batch API.
- `classify-quiz-scope.mjs` (subcommands: `test|submit|status|collect|recheck|recheck-collect|tag-domains|tag-domains-collect`) — scope-classifies and domain-tags each question against this app's own `domainData.ts`/`ServiceScope.tsx` as grounding context, also via the Batch API. Writes each question's `domain` field (what `examSampling.ts` depends on) and a report to `others/quiz-scope-report.json`.
- `apply-quiz-scope-cleanup.mjs` — applies that report: drops off-topic sets/questions, regenerates `meta.ts`.

These need `ANTHROPIC_API_KEY` set and are billed on that key. **Run them manually with `node scripts/<name>.mjs` when the user explicitly asks — never invoke them proactively from a Claude Code session**; they're not part of `npm run build`/`dev` and re-running them (especially the batch-API ones) has a real dollar cost and can overwrite hand-tagged domain data.

### Mobile layout

Single breakpoint at `720px` (`@media (max-width: 720px)` in `index.css`; a matching `min-width: 721px` block holds desktop-only rules). The master-detail pattern (domain pages, quiz sessions) mounts only ONE of {sidebar, panel} at a time on mobile (`mobileDetailActive` state + a `key`-remount with a CSS slide-in animation) instead of squeezing both into one flex row — see `DomainDetail.tsx` and `QuizSessionPage.tsx`. Split containers use `overflow-x: clip`, not `overflow-x: hidden` — `hidden` implicitly forces `overflow-y: auto` per the CSS spec, which breaks `position: sticky` on descendants (this bit us once; there's an inline comment at the relevant rule — don't "simplify" it back to `hidden`).

### Theming

`src/index.css` defines light tokens on `:root` and dark overrides under both `@media (prefers-color-scheme: dark)` and `:root[data-theme="dark"]`. `ThemeToggle.tsx` (mounted once, fixed top-right, in `App.tsx`) sets `data-theme` on `<html>` and persists the choice to `localStorage` (key `'theme'`). `index.html` has an inline pre-React script that applies the stored theme before mount, to avoid a flash of the wrong theme — keep that in sync if the storage key or values change.

### Deployment

GitHub Pages, deployed via `.github/workflows/deploy.yml` (Actions-based, triggers on push to `main`) — **not** the legacy branch-based Pages build. The repo's Pages source (`build_type: workflow`) is a setting on GitHub itself, not something in this repo, so a freshly created repo pointed at this code needs `gh api -X PUT repos/<owner>/<repo>/pages -f build_type=workflow` once, or the legacy build will try to serve `dist`-less raw source and fail.
